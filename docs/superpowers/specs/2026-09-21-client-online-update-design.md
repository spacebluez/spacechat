# SpaceChat 客户端在线更新设计

## 目标

用户首次安装后，在 Windows x64 或 Linux x64 终端输入 `spacechat` 即可启动客户端。此后客户端只从本次连接的 SpaceChat 服务端检查并获取更新，不再人工分发每个版本的 `.exe`。

服务端同时发布最新客户端版本和最低兼容版本：兼容的旧客户端可以跳过更新，不兼容的旧客户端必须更新后才能进入聊天室。更新失败不得损坏当前可用版本。

## 范围与边界

- 首期仅支持 Windows amd64 和 Linux amd64。
- 首次安装允许使用一次性安装器或安装命令；存量用户需要完成这一次迁移。
- 默认服务端由安装配置写入，继续支持 `spacechat --server <ws-or-wss-url>` 临时切换。
- 更新清单和安装包只由本次连接的 SpaceChat 服务端下发，不使用 GitHub、GitLab、winget、apt 等发布源。
- 本期不实现差分更新、后台静默更新、多发布渠道、ARM、自动降级或服务端控制的远程命令执行。
- 更新检查发生在进入聊天界面之前；客户端不会在未确认时自动下载安装。

## 方案选择

采用“稳定入口 + 版本化客户端”的结构。

稳定入口 `spacechat` 只读取当前版本指针、启动对应的版本化客户端并透传命令行参数。联网检查、交互、下载、校验、安装和重新启动都由版本化客户端完成。客户端安装新版本时写入新的版本目录，不覆盖正在运行的程序，因此 Windows 和 Linux 使用同一套更新模型；更新逻辑本身也能随客户端升级。

未采用以下方案：

- 单个可执行文件覆盖自身：Windows 需要额外等待和替换进程，失败恢复复杂。
- 固定联网启动器加聊天子程序：启动器协议和安全逻辑难以在线演进。
- 操作系统包管理器：不符合只能由 SpaceChat 服务端下发的约束，并会增加管理员权限和多套发布流程。

## 本地布局

Windows 使用用户级目录，不要求管理员权限：

```text
%LOCALAPPDATA%\SpaceChat\
  bin\spacechat.exe
  config.json
  current
  versions\0.4.0\spacechat-client.exe
  versions\0.4.1\spacechat-client.exe
  tmp\
```

安装器将 `%LOCALAPPDATA%\SpaceChat\bin` 加入用户 `PATH`。

Linux 使用 XDG 目录：

```text
~/.local/bin/spacechat
${XDG_CONFIG_HOME:-~/.config}/spacechat/config.json
${XDG_DATA_HOME:-~/.local/share}/spacechat/
  current
  versions/0.4.0/spacechat-client
  versions/0.4.1/spacechat-client
  tmp/
```

`current` 是内容仅包含规范三段式版本号的普通文件，避免 Windows 符号链接权限问题。更新时通过同目录临时文件加原子重命名切换。入口拒绝包含路径分隔符、预发布标记或非 `MAJOR.MINOR.PATCH` 格式的内容。

入口仅允许启动受管 `versions/<current>/spacechat-client[.exe]`，不接受配置中的任意可执行路径。所有参数和终端输入输出原样交给版本化客户端。

## 服务端更新接口

更新接口与现有 HTTP/WebSocket 服务使用相同监听地址，并继续受来源网段限制保护。

- `GET /updates/v1/manifest`：返回清单的原始 JSON 字节。
- `GET /updates/v1/manifest.sig`：返回清单的 Ed25519 分离签名。
- `GET /updates/v1/artifacts/<固定文件名>`：流式返回清单引用的安装包。

客户端将 `ws://host:port/ws` 映射为 `http://host:port/updates/v1/...`，将 `wss` 映射为 `https`。忽略 WebSocket URL 的 `/ws` 路径，不允许更新清单把客户端重定向到其他主机。

服务端从只读更新目录加载文件。启动时校验清单结构、签名、版本关系、文件名、大小和 SHA-256；部署内容不一致时不发布该清单，也不启用对应的最低版本限制。下载处理只允许清单中列出的固定文件，禁止客户端提供文件系统路径。

清单结构为：

```json
{
  "schema": 1,
  "latest_version": "0.4.0",
  "minimum_supported_version": "0.3.2",
  "release_notes": "修复连接问题并增加在线更新",
  "artifacts": {
    "windows-amd64": {
      "file": "spacechat-client-windows-amd64-0.4.0.exe",
      "size": 12345678,
      "sha256": "64位小写十六进制摘要"
    },
    "linux-amd64": {
      "file": "spacechat-client-linux-amd64-0.4.0",
      "size": 12345678,
      "sha256": "64位小写十六进制摘要"
    }
  }
}
```

版本号仅接受三段非负十进制整数，不接受前导零、预发布或构建后缀。必须满足 `minimum_supported_version <= latest_version`，两个首期平台的制品都必须对应 `latest_version`。

Ed25519 签名覆盖清单文件的原始字节，清单内 SHA-256 覆盖制品内容。客户端内置发布公钥；发布私钥只由发布人员或受控构建环境持有，不提交仓库，也不部署到聊天服务器。即使传输链路为明文，客户端也不会执行未被正式发布密钥授权的程序。

## 启动与更新流程

1. 稳定入口读取 `current` 并启动当前版本化客户端。
2. 客户端解析实际服务端地址：命令行 `--server` 优先，否则使用安装配置。
3. 客户端以短超时获取清单和签名，先验证签名，再解析清单并选择当前平台制品。
4. 客户端比较自身版本：
   - `current == latest`：直接进入登录界面。
   - `minimum <= current < latest`：显示 `Update / Skip`。
   - `current < minimum`：显示 `Update / Exit`，禁止进入聊天。
   - `current > latest`：视为开发或回退中的服务端，允许继续但记录提示，不自动降级。
5. `Skip` 只对本次启动有效，下次启动重新提示。
6. 用户选择更新后，客户端将制品下载到受管 `tmp` 目录，限制响应大小并校验实际字节数和 SHA-256。
7. 客户端把制品移入新的版本目录，设置平台所需执行权限，再用隐藏参数 `--self-check` 启动新程序完成本地自检。
8. 自检通过后原子写入 `current`，以原命令行参数启动新版本并结束旧进程。
9. 下一次正常启动时清理无效临时文件，并只保留当前版本和最近一个旧版本。Windows 上仍在使用而无法删除的旧文件留待下次启动处理。

同一台机器只允许一个更新操作修改 `current`。客户端使用安装根目录中的更新锁；无法获得锁时重新读取 `current`，若另一个进程已经完成目标更新则直接启动新版本，否则提示稍后重试。

## 交互与失败处理

更新提示在 Bubble Tea 聊天界面启动前显示，包含当前版本、目标版本、简短说明和明确选项。

- 可选更新：`Update / Skip`。
- 强制更新：`Update / Exit`，不能跳过。
- 用户确认前不下载、不修改本地文件。
- 下载显示已接收字节和总大小；本期不实现暂停或断点续传。
- 可选更新下载、校验、自检或安装失败：删除未完成文件，保留原版本，允许继续聊天。
- 强制更新失败：保留原版本，只提供 `Retry / Exit`。
- `current` 切换前的任何失败都不会影响旧客户端。
- 切换后启动新版本失败时恢复旧 `current`，显示错误并从旧版本继续执行可选更新流程；强制更新仍不得进入聊天。
- 更新检查超时或接口暂时不可用时允许启动当前客户端，最终兼容性由 WebSocket 握手强制执行。
- 清单签名错误、摘要错误、文件超限或路径异常按安全错误处理，绝不执行下载内容。

## 服务端兼容性强制

WebSocket `join` 请求新增以下可选字段：

```json
{
  "client_version": "0.4.0",
  "client_os": "windows",
  "client_arch": "amd64"
}
```

服务端在读取房间、历史或成员信息前比较客户端版本与已验证清单中的 `minimum_supported_version`：

- 版本满足要求：继续现有鉴权和加入流程。
- 版本缺失、格式错误或过低：返回 `upgrade_required`，包含最低版本和用户可读提示，然后关闭连接。
- 平台不受支持：返回 `unsupported_client`。

客户端识别 `upgrade_required` 后退出聊天连接并返回更新流程，不能通过直接运行版本化客户端绕过强制更新。旧客户端无法识别新错误时也会被服务端关闭，因而不能进入不兼容服务。

为支持平滑迁移，最低版本可配置为 `0.0.0`；此时缺失版本字段的存量客户端暂时允许连接。推荐发布顺序：

1. 部署支持更新接口和新握手字段的服务端，最低版本保持 `0.0.0`。
2. 向存量用户提供最后一次人工安装，切换到 `spacechat` 入口。
3. 确认迁移后，将最低版本提高到首个支持在线更新的客户端版本。

## 发布与部署

构建流程输出：

- Windows amd64 稳定入口和版本化客户端。
- Linux amd64 稳定入口和版本化客户端。
- 两个平台的一次性用户级安装包或安装脚本。
- 服务端程序。
- 清单、分离签名和清单引用的客户端制品。

签名步骤必须显式提供发布私钥；未提供私钥时允许开发构建，但不得生成可部署的正式更新清单。构建日志不得输出私钥内容。

服务端发布包将制品部署到新目录，完成权限、大小、摘要和签名检查后，最后原子切换更新目录或清单。兼容发布只提高 `latest_version`；协议不兼容发布同时提高 `minimum_supported_version`。回退服务端时必须一并回退清单和最低兼容版本，不能只替换服务端二进制。

## 代码边界

- `cmd/spacechat`：稳定入口，只定位并启动当前版本。
- `cmd/xchat`：版本化聊天客户端，在进入 TUI 前调用更新流程并在 join 中上报版本。
- `internal/update`：版本解析、清单验证、签名、下载、文件安装、锁和版本切换。
- `internal/updateui`：终端更新选择和进度交互，不依赖聊天模型。
- `internal/protocol`：客户端版本字段和升级错误载荷。
- `internal/server`：更新 HTTP 端点和 WebSocket 最低版本校验。
- `scripts` 与 `deploy/rooms`：跨平台制品、签名、安装和服务端更新目录部署。

更新模块不读取房间口令、不依赖聊天状态，也不修改聊天数据库。服务端更新文件与 SQLite 数据目录分离。

## 验收与测试

自动化测试至少覆盖：

- 严格版本解析和所有版本比较分支。
- 原始清单签名、错误公钥、被篡改清单、摘要不符、超限下载和路径穿越拒绝。
- Windows/Linux 路径布局、参数透传、无效 `current`、原子切换和并发更新锁。
- 可选更新的 Update/Skip、失败继续和下次重新提示。
- 强制更新的 Update/Exit、失败 Retry/Exit，以及不能进入聊天。
- 新版本自检失败和切换后启动失败回退。
- 服务端仅暴露清单列出的制品，并正确处理 Range 之外的普通完整下载。
- WebSocket 对缺失、错误、过低、满足和高于最新版本的客户端进行兼容性判定。
- 更新检查失败时当前客户端仍可启动，但不兼容版本最终被服务端拒绝。
- Windows amd64 与 Linux amd64 的安装后均可直接执行 `spacechat --version` 和 `spacechat`。
- 现有房间隔离、加密存储、清理、重连、F2 切房和多行输入回归保持通过。

发布验收还需在临时服务实例完成一次可选升级、一次强制升级、一次损坏制品拒绝和一次旧版本回退演练，不接触现有旧服务及数据库。
