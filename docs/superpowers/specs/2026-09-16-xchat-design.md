# XChat 内网聊天室设计

日期：2026-09-16
状态：用户已确认，源码、构建产物与部署已交付；验收记录见 docs/verification-2026-09-16.md。

## 1. 目标与范围

使用 Go 实现服务端及 Windows x64 TUI 客户端。服务端部署到 dev216，客户端交付 xchat.exe。仅供公司内网使用，只有一个公共聊天室，输入昵称即可进入。

不做账号密码、私聊、多房间、文件传输或撤回。昵称不是身份凭证，离线后可被其他人使用；所有连接者均可查看公共历史。

## 2. 已确认技术方案

- Go 服务端通过 WebSocket/JSON 与客户端通信。
- Go 客户端使用 Bubble Tea 实现 TUI。
- SQLite 在服务端持久化消息，不依赖客户端保存记录。
- 首次加载最近 100 条，向上翻页每批最多 100 条，历史持续保存、不自动过期。
- 先持久化再广播，断线自动重连并补齐消息，不自动重发结果不明的消息。

备选为自定义 TCP 协议，第一版不采用，以避免自行维护消息分帧规则。依赖版本在实施阶段核验并固定于 go.mod/go.sum；SQLite 优先使用纯 Go 驱动。

## 3. 组件职责

| 组件 | 职责 | 依赖 |
| --- | --- | --- |
| 服务端入口 | 配置、监听、健康检查、优雅退出 | 聊天服务、存储 |
| 聊天服务 | 会话、昵称占用、事件排序、同步、广播 | 协议、存储 |
| 存储模块 | 建表、保存、游标分页 | SQLite |
| 协议模块 | 请求、事件及错误码 | Go 标准库 |
| 客户端网络模块 | 连接、心跳、重连、同步 | 协议、WebSocket |
| 客户端 TUI | 昵称页、聊天页、发送状态、翻页 | 网络模块、Bubble Tea |

网络操作不得阻塞 TUI 更新循环。每个 WebSocket 连接只有一个串行写入路径。

## 4. 进入与在线状态

昵称去除首尾空白后为 1–20 个 Unicode 字符，拒绝控制字符，区分大小写。服务端原子检查在线昵称，重名拒绝进入并允许客户端修改昵称。加入成功返回在线列表和历史消息。连接结束释放昵称，异常断线依赖心跳超时释放。

进入和退出更新在线列表，系统提示不写入聊天历史。重连遇到旧连接尚未释放昵称时退避重试，不强制踢出同名连接。

## 5. 协议和可靠性

JSON 信封包含 type、request_id、payload。客户端请求包含 join、send、history、sync；服务端事件包含 welcome、message、ack、history、sync_complete、presence、error。request_id 用于关联响应，不作为身份凭证。

消息字段为 id、nickname、body、created_at。服务端生成单调递增 ID 和 UTC 时间，客户端按本地时间显示，以 ID 排序和去重。昵称来自会话，不信任客户端声明的作者和时间。正文支持中文，拒绝全空白、控制字符和超过 2,000 个 Unicode 字符的内容。

### 5.1 发送流程

聊天服务串行提交消息，SQLite 提交成功后广播，并向发送者确认消息 ID；写入失败返回错误、不广播。发送者依据确认或关联的广播消除待确认状态。断线时仍未确认的消息显示“结果未知”，不自动重发，由用户查看同步记录后决定是否手动发送。

### 5.2 历史分页

首次返回最近 100 条，按 ID 升序显示。向上翻页使用排他的 before_id 游标，每次最多 100 条，同时返回是否存在更早记录。翻页保持当前阅读位置；正在阅读历史时，新消息不强制滚动到底部。

### 5.3 重连与实时消息衔接

心跳默认每 20 秒一次，60 秒无有效响应关闭连接。重连采用带少量随机抖动的指数退避，基础间隔从 1 秒增至最多 30 秒，退出时停止重试。断线禁用发送，保留草稿。

服务端在串行事件处理路径中建立订阅并捕获消息上界 H。首次加载或重连补齐只查询不超过 H 的消息；H 之后的新事件进入连接有界队列。同步完成后按序发送缓存事件，随后进入实时接收。同步、确认和实时事件通过同一连接写入路径输出。

客户端保留最后连续同步的消息 ID，以 after_id 分批补齐，每批最多 100 条，收到同步完成事件后进入正常状态。队列溢出时关闭慢连接，客户端重连补齐，不能静默丢消息或阻塞所有用户。

数据库元数据保存稳定的聊天室实例 ID。数据库重建或替换导致实例 ID 改变时，客户端清空旧游标并重新加载最新页。客户端进程重启按首次加入处理，不保存本地历史。

## 6. 数据持久化

messages 表包含 id（INTEGER PRIMARY KEY AUTOINCREMENT）、nickname（TEXT）、body（TEXT）、created_at（TEXT，UTC）。元数据表保存实例 ID 和 schema 版本。单服务端进程串行写消息，启用 WAL 和合理 busy timeout。

数据库置于独立持久化目录，不随二进制替换。启动无法打开数据库时明确失败；磁盘写入失败不得报告发送成功。没有自动清理策略，需关注磁盘容量。备份默认停止服务后复制数据库及存在的 WAL 文件再启动，不将运行中直接复制主数据库文件视为可靠备份。

## 7. TUI 交互

- 登录页显示服务器地址、昵称输入和连接错误。
- 聊天页顶部显示连接状态，中部消息区和在线列表，底部输入区及快捷键说明。
- Enter 发送单行文本，PgUp/PgDn 浏览，向上到达已加载历史边界时加载更早消息，Ctrl+C 退出。
- 支持中文输入、粘贴、按显示宽度换行和窗口大小调整；窄窗口隐藏在线侧栏并保留人数。
- 聊天内容按纯文本展示，不能执行终端转义序列。
- 加载历史、发送失败、昵称冲突及重连状态必须明确可见。

## 8. 配置与部署

部署前通过 SSH 只读检查 dev216 的系统、架构、服务管理方式、目录权限和端口。建议初始端口 18080，实际启用前检查占用。服务端可配置监听地址和数据库路径，提供不暴露聊天内容的 /healthz。

如为支持 systemd 的 Linux，提供匹配架构的二进制及 systemd 单元，使用专用非 root 账号和独立数据目录，配置开机启动。若环境不同，先说明差异再调整。不覆盖已有数据、不干扰现有服务、不随意重启主机。防火墙仅向公司内网开放。

Windows amd64 客户端交付 xchat.exe，支持 --server 覆盖服务器地址。默认地址根据实际环境写入构建配置，必须是客户端可达的内网 IP 或 DNS，不能假设 SSH 别名 dev216 能被其他电脑解析。

第一版拟采用可信内网 ws 明文连接，不提供传输加密或身份保证；如果公司要求 TLS，则启用 WSS 后上线。本工具不默认开放公网。交付包括客户端、对应平台服务端、部署配置及使用说明。

## 9. 验收标准

1. 两个不同昵称的客户端双向收发中文消息，在线列表一致。
2. 同名并发加入只有一个成功，另一个得到明确提示。
3. 保存超过 200 条后首次只加载最近 100 条，连续翻页无重复遗漏且顺序正确。
4. 服务端重启后历史仍在，客户端可以重连。
5. 断线期间新增超过 100 条消息，重连后分批补齐，同步期间新消息不丢失。
6. 模拟写入失败不广播；确认丢失时显示结果未知且不自动重发。
7. 慢连接不阻塞其他用户，昵称、正文长度及控制字符校验有覆盖。
8. Windows x64 客户端能启动、输入中文、缩放窗口、翻页和退出。
9. dev216 健康检查通过，启动配置启用；实际主机重启验证需另获许可，不能以配置启用冒充重启验证。
